## Change f06-campaign-create
#### 4.6 F-6: Campaign creation with slot check and plan calculation

Description: The user creates a campaign and assigns slots (ТЗ §8).

Roles: R-1.

Acceptance criteria:

1. The form has: name, advertiser, start and end dates, 1 or more screens, show hours, number of 5-second slots per 1-minute cycle, creative (ТЗ §8, §14.4).
2. The cycle is 60 seconds with 12 slots of 5 seconds. The cycle length is one setting (ТЗ §2, D-1).
3. Creative: the user picks 1 of 3–4 ready placeholders, or uploads a 5-second video file (D-8). Videos of another length are out of scope (ТЗ §8).
4. Before save, the form shows availability and planned shows. Planned shows per screen per day = slots per cycle × 60 × show hours inside the screen working hours. Example: 1 slot, 08:00–20:00 → 720 per screen per day; 3 screens → 2 160 per day (ТЗ §8, §14.5).
5. The check runs per screen × day × hour. A slot taken by one campaign cannot go to another campaign on the same screen in the same hour (ТЗ §8, §14.6, D-9).
6. If free slots are not enough, the form shows a clear message that names the screens and hours in conflict. The campaign is not saved (ТЗ §8).
7. No shows are planned outside the selected dates and hours (ТЗ §8).
8. After save, the campaign appears in the list and in «Расписание». It stays after a page refresh (ТЗ §8, §14.7).
9. A new campaign has 0 shows by the log until «Смоделировать показы» runs (ТЗ §12).

Notifications: None.

# 2. Contract summary (locked; reference, never redefine)

## 2.1 Role and access
One role `admin` = R-1. Every valid demo session is admin; no accounts, no per-record scope. Every public query/mutation takes `sessionId: v.string()` and calls `requireActor(ctx, args.sessionId)` (convex/lib/auth.ts) FIRST. Only `demo.signIn` and `demo.sessionStatus` are exempt. No public actions in phase 1 (an action would call an internal query that runs `requireActor`). UI hiding is never the control. Internal functions need no session. Every public function needs `args` and `returns` validators.
Permissions (yaml contract): `screens.read`, `campaigns.read`, `campaigns.create`, `campaigns.uploadCreative`, `showLog.read`, `showLog.simulate`, `demo.reset`: all `{admin: all}`. Matrix: screens/screenEvents seed-only writes; campaigns create only (F-6), no update, no delete except reset; showLog written only by F-10 «Смоделировать показы» (replace on rerun) or seed; no public function sets any status; clients sending a `status` arg are rejected by validators.

## 2.2 Tables (convex/schema.ts; exported validators `city`, `screenStatus`, `creative`)
- `screens`: code (string, unique "AST-001"), name, city (`astana|karaganda|atyrau|east_kz`), address (synthetic), lat, lng, status (`online|offline`), workStartHour (int 0..23), workEndHour (int 1..24, > start; 24/7 = 0..24), hasCamera (bool), hasVehicleMetric (bool), imageKey (file under public/demo/screens/). Indexes: `by_code [code]`, `by_city [city]`.
- `campaigns`: name, advertiser (text, no advertisers table), startDate, endDate ("YYYY-MM-DD", inclusive, end >= start), startHour (int 0..23), endHour (int 1..24, exclusive, > start), slotsPerCycle (int 1..12), screenIds (Id<"screens">[], 1..100, unique), creative (`{kind:"placeholder", key}` key in PLACEHOLDER_KEYS | `{kind:"video", storageId: Id<"_storage">}`). No status field (computed). No indexes (scan allowed; ~10-15 campaigns). Creation order = `_creationTime`.
- `showLog`: campaignId, screenId, date, shows (int >= 0, <= planned of that screen/day). Indexes: `by_campaign [campaignId, date]`, `by_date [date]`.
- `screenEvents`: screenId, at (ms), kind (`went_offline|back_online`). Index `by_screen [screenId, at]`. Seed has one `went_offline` per offline screen.
- `demoSessions`: sessionId (36-char UUID), expiresAt. Index `by_sessionId`. Base only.
- Not stored: campaign status, slot occupancy, planned shows, audience analytics, notifications, cycle setting, advertisers. Features add no tables unless the change says so with a `## Data` section; adding fields/tables to base tables = CONTRACT_CHANGE_NEEDED.
- Seed (D8): 100 screens (4 regions, some offline, some camera, most 07-23, few 24/7, vehicles ~half), 10-15 «Demo …» campaigns incl. the 3 named (F-5 AC1), one ending within 3 days, one «Завершена», show log for the 2 active named campaigns, dates relative to seed day. Seed keeps every hour <= 12 slots. `demo.reset` deletes campaigns/showLog/screenEvents/screens + uploaded videos and reseeds in one transaction; sessions kept. Seed ids change on reset (saved links break; accepted).

## 2.3 Statuses and notifications
Campaign (computed by `campaignStatus(c, today)`, today = UTC+5): `planned` «Запланирована» (today < start) -> `active` «Активна» (start <= today <= end) -> `finished` «Завершена» (today > end). Screen: `online` «онлайн» / `offline` «офлайн» (stored, seed only). Slot: «Свободно» or campaign name. Screen event labels: `screenEvents.went_offline` «Экран недоступен», `back_online` «Экран снова онлайн».
Notifications (computed by `notifications(screens, campaigns, today)`, shown by F-2): `screen_offline` «Экран недоступен» + screen name; `campaign_ending` «Кампания скоро завершится» + campaign name when 0 <= endDate - today <= 3 days (D-5). Screens first, then campaigns by end date.

## 2.4 Error codes (convex/lib/errors.ts; backend sends codes, never Russian)
`fail(code, details?)` throws `ConvexError({...details, code})`. Codes (ru text in `errors.<CODE>`): UNAUTHENTICATED; WRONG_PASSWORD (returned, not thrown, by signIn); RATE_LIMITED `{retryAfter ms}` (thrown as `ConvexError({kind:"RateLimited", name, retryAfter})` by `enforceRateLimit`); INVALID_INPUT `{field}`; NOT_FOUND `{entity}` (reads by id: F-4, F-5, F-9, F-10); SLOT_CONFLICT `{conflicts: Conflict[]}` (F-6 `campaigns.create`; F-6 owns the front format of `{list}`: group by screen and hour ranges); CAMPAIGN_NOT_STARTED (F-10); INVALID_CREATIVE (F-6); UNKNOWN (front fallback). Adding a code = CONTRACT_CHANGE_NEEDED. Each negative scenario names its code. Validate dates with `requireDate(s, field)` / `isDate`; period length <= `MAX_PERIOD_DAYS` (366), else INVALID_INPUT.

## 2.6 Shared pure functions (convex/lib; no ctx; usable in Convex and front)
Types: `DateStr` ("YYYY-MM-DD"); `ScreenRule` = screens fields `_id, code, city, status, workStartHour, workEndHour, hasCamera, hasVehicleMetric`; `CampaignRule` = campaigns fields `_id, _creationTime, name, startDate, endDate, startHour, endHour, slotsPerCycle, screenIds` (full docs satisfy both); `Slot = {index 1..12, startSec, endSec, campaignId|null, campaignName|null}`; `Conflict = {screenId, date, hour, free, requested}`.
- config.ts: `CYCLE_SECONDS=60`, `SLOT_SECONDS=5`, `SLOTS_PER_CYCLE=12`, `CYCLES_PER_HOUR=60`, `SOON_END_DAYS=3`, `SESSION_DAYS=7`, `MAX_PERIOD_DAYS=366`, `VIDEO_TYPES=["video/mp4","video/webm"]`, `VIDEO_MAX_BYTES=20 MiB`, `PLACEHOLDER_KEYS=["placeholder-1".."placeholder-4"]`, `CITIES`, type `City`. Slot math reads only these.
- time.ts: `KZ_OFFSET_HOURS=5`; `kzNow(nowMs) => {date, hour}`; `isDate(s)`; `requireDate(s, field) => DateStr` (throws INVALID_INPUT); `addDays(d,n)`; `diffDays(a,b)` (b - a); `datesInRange(from,to)` inclusive.
- slots.ts: `isOn(c, s, date, hour)`; `hourSlots(s, date, hour, campaigns) => Slot[12]` (campaigns fill from slot 1 in creation order); `usedSlots(s, date, hour, campaigns) => number`; `plannedShowsForDay(c, s, date, untilHour?)`; `plannedShows(c, screens, from, to) => {total, byDay:[{date,shows}], byScreen:[{screenId,shows}]}` (period clipped to campaign dates); `occupancy(screens, campaigns, from, to) => {occupied, total, percent(1 decimal), byDay:[{date,occupied,total,percent}]}` (D-3; 0 when total 0); `findConflicts(req{startDate,endDate,startHour,endHour,slotsPerCycle,screenIds}, screens, campaigns) => Conflict[]` (D-9; empty = fits).
  Rules: campaign is on for screen S, date d, hour h only if S in screenIds, d in dates, h in [startHour,endHour) and h in S working hours. Planned per screen per day = slotsPerCycle x 60 x show hours inside working hours (SoW example: 1 slot, 08-20, 3 screens = 720 per screen, 2 160 per day).
- status.ts: `campaignStatus`, `notifications` (types `CampaignStatus`, `Notification = {kind, refId, name}`).
- analytics.ts: `audienceHour(s, date, hour) => Audience|null`, `audienceDay(s, date)`, `audienceProfile(s) => {age:{"18-24","25-34","35-44","45-54","55+"}, gender:{male,female}}|null`; `Audience = {people, gazeEstimated, looks, vehicles: number|null}`. null without camera (UI «нет камеры», adds 0 to totals); vehicles null without `hasVehicleMetric`; 0 outside working hours; looks <= gazeEstimated <= people; day = sum of 24 hours. Deterministic from screen code + date. Age/gender are percents summing to 100 and carry the note «предположительно» (algorithm estimate).
- showLog.ts: `simulateShowLog(c, screens, nowMs) => {screenId,date,shows}[]` (online screens only, start date..min(end,today), today counts finished hours only, shows = floor(planned x f), f in 0.85..1.0 by hash; none if not started).
- hash.ts: `hash01(...parts)`; no `Math.random` anywhere (determinism).
- errors.ts: `ERROR_CODES`, `ErrorCode`, `fail`.
- Spec capabilities already archived (do NOT re-specify, reference by name): `app-shell`, `audience-analytics`, `demo-access`, `demo-data`, `show-log`, `slot-model`, `statuses`. Your specs are new capabilities with new names (e.g. `dashboard`, `billboard-list`, `billboard-card`, `campaign-list`, `campaign-create`, `schedule`, `audience-screen`, `reports`, `simulate-shows`), not deltas.
